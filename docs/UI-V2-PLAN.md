Шаг 0 из [UI-V2.md](UI-V2.md). Аудит сделан по ветке `ui-v2` от `main` = e481194 (BrickPad 1.2 alpha); код этой
ветки совпадает с установленной на Brick сборкой 1.2 (отличия только в комментариях). Если план и ТЗ расходятся,
прав ТЗ.

### 1.2 Где смешаны ввод, отрисовка и логика

**Ввод.** Одна функция `key_event` (177 строк, `main.c:3191`) плюс 17 обработчиков `*_key` (по одному на окно).
Внутри `key_event`:
- **Режимы — набор флагов вместо стека экранов:** `browsing`, `slicing`, `rolling`, `randing`, `picking`,
  `presetting`, `theming`, `iconing`, `ducking`, `asking`, `naming`, `exporting`, `learning`, `perform`,
  плюс `tab` (GRID/INSTRUMENT/PATTERNS/FX/MIXER/PROJECT), плюс подрежимы `cl_deep`, `fx_page`, `srow`/`scol`/`lane`.
  В коде 169 упоминаний этих флагов. Приоритет задаётся порядком `if` в `key_event` и тем же порядком
  в `draw()` (`main.c:5655`); новое окно приходится вписывать в оба места.
- **Действия прямо в обработчике кнопок:** mute (`t->mute = !t->mute`), solo, смена паттерна,
  BEND автоматизации, нота прослушивания (`song.lnote`), выбор пэда, рисование шагов (`paint_*`). Всего около
  94 прямых записей в `song.*` по `main.c`, многие внутри `key_event` и `*_key`.
- **Зависимость от экрана в каждом условии:** `tab == T_SEQ && srow >= 1 && srow <= 2 && !cur_pat(sel)->mode`
  повторяется десятки раз. «Где я» описывается не объектом экрана, а комбинацией глобальных переменных.
- **Тап/удержание/комбинация** решаются массивами `held[]`/`used[]` вручную в каждой ветке. Работает надёжно,
  это надо сохранить как есть и вынести в общий слой ввода.

**Действия, которые уже вынесены (хорошая база для шага 1):** `clip_toggle`, `play_key`/`play_release`, `listen`,
`undo`/`push_undo`/`edit_begin`, `copy_paste`, `delete_action`, `edit_tap`, `edit_arrow`, `par_adjust`, `par_default`,
`pat_switch`, `freeze_set`, `capture`, `rnd_open`, `tab_step`/`tab_project`/`set_tab`, `step_*`, `roll_*`.
Но часть из них сама смотрит на `tab`/`srow` и решает, что делать (`edit_tap`, `delete_action`, `copy_paste`
ведут себя по-разному на разных экранах): это «действия, знающие экран», их нужно разделить на
чистое действие + выбор в экране.

**Отрисовка.** `draw()` выбирает одну функцию `draw_*` (их около 40). Отрисовка в основном только читает данные,
но есть исключения: `draw_marquee`/`draw_*_live` держат таймеры, `draw_gb_cached` кеширует панель в текстуру
(это правильно, оставить). Подвал: `draw_footer(строка)` — 27 мест, строка подсказок собирается тут же
по состоянию курсора. Тосты: `toast()` — 141 вызов.

**Частота кадров.** Уже есть `frame_rate()` (`main.c:4865`): 60 fps при нажатых кнопках, 30 при игре, 10 в покое,
сон по 5 мс с пробуждением по событию. Требование ТЗ «≤30 fps / по изменению» почти выполнено: нужно только
ограничить 60 → 30 и добавить флаг «грязно», чтобы в покое не перерисовывать вовсе.

**Аудио.** Звук не ждёт интерфейс: секвенсор внутри колбэка, UI → звук через SPSC-очередь (`engine_trig`,
`engine_set_sample`…), простые параметры звук читает прямо из `song` (int8/int16, атомарно на ARM64).
Слой действий должен сохранить это правило: никаких блокировок, никаких длинных операций в колбэке.

### 1.3 Темы

- Сейчас 10 токенов: `TC_BG, TC_CELL, TC_LINE, TC_GREY, TC_DIM, TC_TEXT, TC_ACCENT, TC_ALERT, TC_SEL, TC_PLAY`
  (`main.c:39`), макросы `C_BG … C_PLAY`, в коде ~930 использований.
- 6 встроенных тем (GRAPHITE, BRICK, PAPER, PHOSPHOR, COBALT, ROSE) массивом в коде; свои темы — файлы
  `themes/ИМЯ.thm` (по строке `r g b` на токен, по порядку; старый файл без новых строк получает цвета GRAPHITE),
  есть редактор тем в PROJECT и проверка читаемости `theme_legible`.
- **Зашитые цвета вне темы:** панели движков `GB_*`, `AB_*`, `CL_*`, `SM_*` (≈20 констант, 336 использований) —
  «как у оригинала». По ТЗ их надо перевести в токены (`eng_*`, `panel`…), а сами панели-«железки» уйдут
  вместе со старыми экранами ЗВУКА на шаге 4.
- **Чего нет из ТЗ:** `panel`, `accent` отдельно от `play`, `eng_sampler/grand/acid/cloud`, `cat_pattern/sound/fx/mod/mix`,
  `warn` и меток движков SMP/GRD/ACD/CLD.
- **Совместимость формата:** файл `.thm` — позиционный список. Новые токены добавляем **в конец** списка: старые
  `.thm` пользователя продолжат читаться (недостающие возьмутся из «Космика»). Формат остаётся «только числа», без имён
  и комментариев: `theme_read` читает его через `fscanf("%d %d %d")` и на любом тексте остановится. Порядок токенов
  задаёт код.

### 1.4 Как описаны параметры движков

- Единый номер параметра `P_*` (`main.c:1144`): базовые параметры сэмплера + диапазоны-смещения
  `P_SX` (SAMPLER DEEP), `P_SY` (GRAND), `P_AC` (ACID), `P_CL`/`P_CX` (CLOUD и DEEP), `P_AX` (ACID DEEP),
  `P_GX` (GRAND DEEP), `P_PT` (гнёзда PATCH). Всего ~150.
- Имена — массив `par_name[P_N]`; подсказки — `hint_*` в `hints.h`.
- **Диапазон и шаг — в коде, а не в данных:** `par_adjust` (49 строк `switch`/`if`), часть диапазонов в
  `sp_range`/`ap_range`/… в заголовках движков, крупный шаг вычисляется условиями (`k == SP_TUNE2 ? 12 : …`).
- **Вывод значения — в коде:** `par_str` (138 строк `switch`).
- **Раскладка — координатами:** таблицы `GbCtl {p, x, y, kind, r}` для каждой панели (`gb_ctl`, `ab_ctl`, `sm_ctl`,
  `cl_ctl`, `ad_ctl`, `gd_ctl`, `cd_ctl`, `sd_ctl`, `pt_ctl`), курсор ходит «к ближайшему в направлении».
- `par_visible` скрывает параметры по режиму WARP.

Итог: имя, порядок и место уже в данных, а диапазон, шаг, формат значения и «страница» — в коде.
Для ТЗ нужна одна таблица `ParDef { id, name, short, lo, hi, step, big, fmt, page, more, hint }` на движок;
`par_adjust`/`par_str` превращаются в общий код по таблице + несколько особых случаев (TYPE, SAMPLE/SRC — файл,
BPM с «tap», BARS по списку, START/END связаны друг с другом).

### 1.5 Проект, формат, настройки

- `.bpp`/`state.bin` = сырая структура `Song` с `STATE_MAGIC 0xB2B2000F` и `_Static_assert` на размер.
  **UI v2 формат не меняет.** Всё новое (вид, полоса пэдов, подсказки, память позиции) — настройки устройства,
  отдельный файл `ui.cfg` рядом с `hints.cfg`/theme-файлом, не внутри проекта.
- Память позиции между запусками не обязательна по ТЗ; держим в памяти, при желании пишем в `ui.cfg`.

### 1.6 Тесты

В рабочей папке на Brick (`brickpad/tests`, в репозиторий не входит) 57 файлов; **41 тест включает `main.c`
целиком** и обращается к его статическим переменным (`tab`, `srow`, `browsing`…) и функциям `key_event`/`draw_*`.
Любая перестройка навигации их ломает. Тесты движка (`qa_engine`, `qa_warp`, `qa_export`, `qa_frz`…) от UI
не зависят и остаются эталоном «звучит как раньше».

### 1.7 Шрифт и кириллица — блокер для русских названий

Шрифт — `font8x8_basic` (только ASCII 0–127), масштабируется ×2/×3, крупный — точками.
В ТЗ и макетах экраны по-русски (ПЭДЫ, ЗВУК, ЯРКОСТЬ…). Кириллицы в шрифте нет. Варианты — решение за
пользователем (см. «Открытые вопросы»).

## 2. Целевая архитектура

```
src/
  main.c        главный цикл, SDL, загрузка/сохранение (то, что останется)
  actions.c/.h  слой действий: всё, что меняет Song/движок (шаг 1)
  input.c/.h    кнопки → события: тап, удержание, комбинация, автоповтор (из held[]/used[])
  ui.c/.h       стек экранов, крошки, подвал, шпаргалка, поп-ап, полоса пэдов, токены темы
  params.c/.h   таблицы ParDef всех движков и FX, общие par_get/par_set/par_str
  scr_*.c       экраны: home, pad, pattern, sound, fx, mod, mix, mixer, scenes, project, simple_*
  theme.c       токены, встроенные темы, .thm
```

Экран:
```c
typedef struct Screen {
    const char *title;                 // для крошек
    int (*pages)(void);                // число страниц (L1/R1), 0 = нет
    void (*draw)(struct Screen *);
    int  (*on_input)(struct Screen *, const Ev *);   // 1 = обработано
    const Bind *binds;                 // таблица «кнопка → действие» = подвал + шпаргалка
    int page, cur, scroll;             // сохранённая позиция
} Screen;
```
Глобальные клавиши (Y назад, F1/F2, L1/R1, SHIFT+стрелка, SHIFT-шпаргалка, PLAY, F1+F2, MENU 3 с) обрабатывает
`ui.c` до экрана; экран получает только своё. Подвал и шпаргалка строятся из `binds` — один источник правды.

Действия: функции с явными аргументами (`act_clip_toggle(pad)`, `act_set_param(pad, id, value)`,
`act_param_step(pad, id, dir, big)`, `act_select_pad(pad)`, `act_mute(pad)`, `act_copy(what)`, `act_paste(what)`,
`act_undo()`, `act_pattern_queue(pad, n)`, `act_freeze(pad, on)`…), без чтения `tab`/`srow`. Undo и `edit_begin`
внутри действий. Простой вид вызывает те же функции.

Пиксельная сетка: 1024×768, крошки 32 px, полоса пэдов «крупная» 56 px, подвал 32 px → рабочая зона ~648 px.
Всё верстаем под крупную полосу.

## 3. План шагов 1–8

Каждый шаг — серия небольших коммитов в `ui-v2`. В конце шага: сборка, запуск на Brick (только при закрытом
BrickPad, сборка через `tools/safebuild.sh`), DEMO/NEON открывается и звучит как раньше (сравнение
`qa_export` рендера NEON до/после — побайтно), коммит, при заметном результате — pre-release `v2.0-alpha.N`.

### Шаг 1. Слой действий (без видимых изменений) — 2–3 сессии
**Сделано 2026-11-13:** `src/actions.h` (act_*), `src/params.h` (par_get/par_put/par_limits), `src/input.h`;
эталонный прогон (3000 шагов + перебор всех параметров) совпадает с 1.2. Модули пока подключаются в `main.c` как
заголовки (одна единица трансляции, как `synth.h`/`fx.h`); раздельная компиляция — на шаге 2.
1. Вынести `actions.c/.h`: собрать существующие действия, дать им явные аргументы.
2. Разделить «действия, знающие экран» (`edit_tap`, `delete_action`, `copy_paste`, `edit_arrow`): экран решает *что*,
   действие делает *как*.
3. Все прямые записи `song.*` из `key_event`/`*_key` заменить вызовами действий.
4. `params.c`: таблица `ParDef` для SAMPLER, GRAND, ACID, CLOUD, DEEP-страниц, FX; `par_adjust`/`par_str` → по таблице;
   проверка: для каждого параметра старые и новые `adjust/str` дают одинаковый результат (тест-перебор).
5. `input.c`: тап/удержание/комбинации из `held[]`/`used[]` в одном месте.
6. Тесты: эталонный рендер NEON (`qa_export`) и прогон движковых тестов; UI-тесты, включающие `main.c`,
   по возможности переводим на действия, остальные помечаем «до шага 2».
**Готово, когда:** сборка 1.2 и новая ведут себя одинаково на всех кнопках и звучат одинаково.

### Шаг 2. Каркас — 2–3 сессии
**Сделано 2026-11-13 (ждёт проверки на Brick):** токены и пять тем ТЗ (81b2e0e), рамка `src/ui.h` (7d34c03): крошки + x/5,
тонкая полоса пэдов, подвал ≤3 подсказок + SHIFT MORE, шпаргалка по SHIFT, поп-ап значения, ≤30 fps. Стек экранов
переносится в шаг 3: он появится вместе с первыми новыми экранами (ПЭД-хаб), сейчас крошки строятся из состояния 1.2.
1. `theme.c`: токены по ТЗ (16 + служебные), «Космик» встроенной темой по умолчанию; старые 6 тем и `.thm`
   читаются (новые токены — в конец, недостающие берутся из Космика). Метки движков SMP/GRD/ACD/CLD.
2. `ui.c`: стек экранов push/pop, память позиции, крошки («NEON › 04 BASS › ЗВУК › ФИЛЬТР», справа «2/5»),
   подвал ≤3 подсказок из `binds`, шпаргалка по удержанию SHIFT, поп-ап значения при удержании EDIT,
   полоса пэдов (СКРЫТА/ТОНКАЯ/КРУПНАЯ; цвет движка, прогресс клипа, выбранный).
3. Глобальные кнопки по ТЗ. Внимание: SHIFT+PLAY не трогать (Knulli убивает приложение), SHIFT+MENU — системный.
4. Старые экраны — «временные экраны» в стеке: каждый `draw_*`/`*_key` обёрнут как `Screen`, флаги режимов
   заменяются положением в стеке.
5. Флаг «грязно» и предел 30 fps.
**Готово, когда:** все функции 1.2 доступны, сверху крошки, снизу новый подвал, тема Космик.

### Шаг 3. ПЭД-хаб и ПАТТЕРН — 2 сессии

### Шаг 4. ЗВУК — 3–4 сессии

### Шаг 6. Настройки ИНТЕРФЕЙС, быстрый прыжок, пустые состояния — 1 сессия

Пустые состояния на каждом экране («Пэд пуст: EDIT — выбрать движок», «Нет шагов: EDIT ставит шаг»…).
Сверка: каждая функция 1.2 доступна в продвинутом виде (чек-лист по MANUAL.md) → слияние в main станет возможным.

## 4. Оценка объёма

- Затронуто ~5000 из 5817 строк `main.c`; `engine.c`, `sample.c`, DSP-заголовки — не трогаем.
- Оценка: **15–20 рабочих сессий** на Brick (сессия ≈ 1–2 ч до лимита), из них шаги 1–2 самые рискованные
  (поведение должно остаться прежним), шаг 4 самый объёмный.
- Ограничения Brick: 1.4 ГБ ОЗУ без swap, сборка `main.c` zig'ом тяжёлая → разбиение на файлы (шаг 1) заодно
  облегчит сборку; собирать через `tools/safebuild.sh`, никогда при открытом BrickPad.

## 5. Риски

- Регресс поведения в шагах 1–2 → эталонный рендер NEON + прогон движковых тестов после каждого коммита.
- Производительность отрисовки на Brick (новые графики) → кеш текстур, предел 30 fps, лог fps уже есть.
- UI-тесты, включающие `main.c`, ломаются при реструктуризации → переписываем по мере шагов, это часть работы.
- Две копии исходников (рабочая `/userdata/claude/brickpad` = 1.2 и клон `brickpad-git` = ветка `ui-v2`):
  правки 1.2 (багфиксы) делаем в main и переносим в `ui-v2`.
